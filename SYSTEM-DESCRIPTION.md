# System Description — Shadow Genesis Reference Service

This description defines the system intended for a SOC 2 readiness assessment.
It is management's description, approved by the sole founder through the
authenticated merge of this change. It does not assert that a CPA has issued a
SOC 2 report or that a Type II observation period has elapsed.

## DC1 — Services provided

The system is a reusable Firebase/GCP starter and reference measurements API.
It demonstrates a secure, continuously verified software-delivery lifecycle:
ticketed changes, protected pull requests, deterministic tests and security
checks, keyless deployment, monitoring, backup/restore controls, and protected
post-merge evidence. The public health and documentation routes expose no
customer data; application data routes require a verified Firebase identity.

## DC2 — Principal service commitments and requirements

Management commits to reasonable protection against unauthorized access and to
operation, monitoring, backup, and recovery practices that support stated
availability objectives. Commitments are documented in
`policies/objectives-and-commitments.md`, the information-security policy, the
BCDR policy, published service documentation, and customer agreements when the
template is adopted. Security and Availability are the only Trust Services
Categories in this readiness scope. Confidentiality, Processing Integrity, and
Privacy features may exist in the example code but receive no readiness score
or compliance claim unless a future scoped assessment explicitly adds them.

## DC3 — System components and boundary

- **Infrastructure:** GCP project `shadow-dk-246464`; Cloud Run; Artifact
  Registry; Firestore Native mode with PITR/backups; Cloud Logging and
  Monitoring; Firebase Hosting for the readiness dashboard; GitHub-hosted CI.
- **Software:** repository `dorkalev/shadow-genesis-20260727-100448`, the
  measurements service, Firestore deny-by-default client rules, `shadow-ci`,
  GitHub Actions workflows, and infrastructure configuration generated by
  Shadow.
- **People:** exactly one human, founder `dorkalev`. AI tools, GitHub Actions,
  Firebase Auth, and GCP service accounts are machine controls—not employees,
  reviewers, or organizational segregation of duties.
- **Procedures:** ticket-first main-only SDLC, incident response, access review,
  vulnerability management, vendor review, backup/restore test, management
  review, onboarding/offboarding, and evidence retention.
- **Data:** source and policy records (Internal); security/audit logs (Internal);
  account identifiers and example service records (Confidential when used with
  real customer data); credentials remain in managed identity/secret systems
  and are not stored in the repository.
- **Boundary:** the GitHub repository and workflows, GCP project and named
  services, Firebase Hosting dashboard, and the founder endpoint used to
  administer them. A copier must replace all identifiers and re-run Genesis;
  this repository's evidence never transfers as the copier's operating proof.

## Logical data flow

1. A client authenticates with Firebase Auth and presents an ID token.
2. Cloud Run verifies the token and authorizes subject-scoped operations.
3. The runtime service account reads/writes Firestore through the Admin SDK;
   direct Firebase client reads and writes are denied by `firestore.rules`.
4. Cloud Audit Logs and application audit records capture administrative and
   sensitive actions; Monitoring evaluates availability signals.
5. A protected PR to `main` runs required tests and scanners. On merge, a
   keyless deploy identity builds an image, resolves its immutable digest, and
   deploys that digest. A separate workflow appends the complete change record
   to protected `compliance-archives`.

## Trust Services Criteria and controls

Security Common Criteria CC1–CC9 and Availability A1 criteria are in scope as
selected in `shadow/scope.json`. The authoritative risk-to-control mapping is
`policies/controls.md`; the deterministic report distinguishes design,
technical configuration, and operating evidence. A 100% readiness result means
all currently machine-testable in-scope checks passed or were truthfully marked
not applicable. It is not an auditor opinion.

## DC4 — Significant incidents and changes

Security events and incidents are recorded under `evidence/security-events/`
and the issue tracker. No significant incident is known as of the approval date.
This statement is re-evaluated at each management review and before providing
the description to a CPA. Significant system or scope changes require a
ticketed update to this description.

## DC5 — Applicable controls and solo-founder limitation

The founder may author and merge the same change. GitHub records the
authenticated merge as management approval; no AI persona is represented as a
second human. Compensating controls are mandatory PRs, required deterministic
checks, dependency/code/secret scanning, no force/deletion on protected
branches, restricted keyless deploy identity, immutable image digests,
post-merge population reconciliation, continuous verification, and independent
CPA examination. The CPA must accept this disclosed control concentration and
will determine whether the controls are suitably designed and, for Type II,
operated throughout the chosen period.

## DC6 — Complementary user-entity controls

Adopters and customers are responsible for protecting their credentials,
enforcing MFA for their users, configuring least privilege, submitting accurate
data, reviewing authorized users, promptly reporting suspected incidents, and
configuring their own commitments, retention, recovery objectives, and scope.
They must not rely on this demo's evidence as proof of their own operations.

## DC7 — Complementary subservice-organization controls

Google Cloud/Firebase and GitHub are treated using the carve-out method.
Physical security, underlying infrastructure, managed platform availability,
and provider administrative controls are outside management's direct operation.
Management reviews provider assurance reports and relevant incidents annually,
records the review under `evidence/subservice/` and `evidence/vendors/`, and
monitors the controls it configures directly. LLM providers are optional
vendors; no LLM is required for daily verification, merge, deployment, or
archive operation.

## Description maintenance

Review annually and upon changes to scope, commitments, architecture,
subservices, data types, or control ownership. Every revision follows the same
protected `main` PR path and is preserved in Git history and the merge archive.
